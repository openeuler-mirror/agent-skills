## Step-by-Step Workflow

### Phase 0: Upstream Environment Initialization
**CRITICAL**: This phase MUST be completed before any other operations.
Use the **`ros-oe-upstream-init`** skill to verify if the user has an existing upstream ROS cache directory (like `ros-oe-upstream-init`). If they do not, you MUST use the skill to fetch and build the upstream cache. This is a prerequisite for all subsequent steps.
**Agent Note on Upstream Warnings**: If the initialization outputs warnings about Bloom release repos or version mismatches, it will generate `bloom_release_repos.log` and/or `version_mismatch.log` in the `output/` directory. Do not stop or fix them here. Just record the log file locations. You will handle specific package fixes lazily in Phase 3.

### Phase 1: Environment Configuration
The user will provide a workspace directory. You must ensure `openeuler_ros_upgrader_env.yaml` exists and contains BOTH `personal_eur_project` and `official_eur_project`, along with other required fields.
Set `current_active_eur_project` to the value of `personal_eur_project` by default. If missing, ASK the user. Do not guess. Create the file and subdirectories (`personal-repos`, `eur_build_logs`, `test_results`) if needed.

### Phase 2: Preparation and Dependency Analysis
Use the **`ros-oe-pkg-prep`** skill to analyze dependencies and generate the final `dependency_list.txt` and `build_layers.txt`.
- If `upgrade_mode` is `explicit`: Follow the skill's instructions for explicit mode (topological sort & multi-repo expansion).
- If `upgrade_mode` is `deep_dependency`: Follow the skill's instructions for deep dependency analysis and layer generation.
After generating the lists, use the **`ros-oe-repo-fork`** skill to fork the required repositories to the user's personal GitCode account.

### Phase 3: Local Package Update (Spec, Patches, Tarball)
**Upstream Pre-check (Mismatches & Bloom Repos)**: Before updating a specific package, check if its repository name exists in the `version_mismatch.log` OR the `bloom_release_repos.log` generated in Phase 0. 
- If it's in `version_mismatch.log`: you MUST correct its upstream tracking branch by appending the `<repo_name> <correct_branch_name>` mapping to the `<upstream_cache_dir>/scripts/ros/<ros_distro>/ros-version-fix` file.
- If it's in `bloom_release_repos.log` (a -release repo): you MUST find its real upstream repository URL and append the `<repo_name> <real_repo_url.git>` mapping to the `<upstream_cache_dir>/scripts/ros/<ros_distro>/ros-url-fix` file.
After applying either fix, delete the old source directory inside `output/src/` and re-run `ros-upstream-setup.sh` to get the correct version and spec.
Use the **`ros-oe-pkg-update`** skill to update all packages locally in the `personal-repos` directory. 
The skill will handle spec updates, tarball downloads, and patch conflict resolution. If the skill pauses for complex patch conflicts, use your code agent capabilities to analyze the C++ source/spec differences and generate a fix.
**Manual Update & Tarball Deletion Rule**: If you ever need to manually update a package (e.g., for non-ROS packages or when fixing updates), you MUST explicitly delete the old tarball. **NEVER use glob patterns like `*.orig.tar.gz`** to match the old tarball, as this is unreliable. Instead, you MUST parse the `Source0` (or relevant `Source` fields) from the **OLD spec file** to determine the exact name of the old tarball and delete it.
**Pre-Commit Code Review (CRITICAL)**: After the `ros-oe-pkg-update` skill finishes updating a package, but BEFORE you commit and push the changes, you MUST review the `git diff` using your agent capabilities. 
The rule is: changes should generally only include expected fields like `Version`, `Release`, `Source0` (tarball name), `%changelog`, `Requires`, and `BuildRequires`. 
Pay extreme attention to the `%build` and `%install` sections. `ros-oe-upstream-init` often misidentifies the build system template (e.g., wrongly replacing existing Python `setup.py`/`pip` build commands with CMake macros, or vice versa). The original openEuler spec's build methodology is almost always correct. If you see the build commands drastically changed (a paradigm shift), you MUST manually revert the `%build` and `%install` sections back to the original openEuler logic, while preserving the new version and dependency updates. Close these errors early in this phase instead of waiting for EUR build failures!
**Patch Verification & Necessity Analysis (CRITICAL)**: If the old spec contained custom openEuler patches (e.g., `Patch0: ...`), the `ros-oe-pkg-update` script might blindly append them back to the new spec (Scenario A). You MUST NOT blindly trust that these old patches still apply to the new upstream tarball. You MUST:
1. Extract the new tarball locally (`tar -xzf <tarball>`).
2. Navigate into the extracted source and test the patch strictly using `patch -p1 --dry-run --fuzz=0 < ../<patch_file>`. (EUR explicitly uses `--fuzz=0`, meaning the patch must match lines exactly).
3. If the patch applies cleanly, delete the extracted folder and proceed.
4. If the patch fails or reports fuzz, you MUST read the new source code. Check if upstream has already fixed the issue (e.g., via git log or inspecting the file). If the fix is already upstream, the patch is obsolete—you must delete the patch file and remove its `Patch0:` line from the spec. If the issue persists but the code context changed, you MUST manually edit the extracted source, regenerate the patch via `git diff`, update the `.patch` file in the repo, and verify it applies cleanly.
**CRITICAL REQUIREMENT BEFORE PROCEEDING TO PHASE 4**: Once all packages are locally updated, conflict-resolved, and diff-reviewed, you MUST explicitly commit (`git add . && git commit -s -m "..."`) and push (`git push`) the local modifications from the `personal-repos` directory to the user's remote GitCode repository. Failure to push will cause the EUR cloud build to fetch old code. 
**Append-Only Memory Rule**: After committing a package, you MUST append a brief, human-readable summary of the changes (what was changed, conflicts resolved, patches removed) to `reports/02_update_summary.md` so that you can remember these details later in Phase 6 for PR generation.

### Phase 4: EUR Cloud Building and Repository Publication
**CRITICAL**: If you discover the need to build additional dependency packages or adjust the build order during personal building or testing, you **MUST** synchronously update `build_layers.txt`. The official build in Phase 7 will strictly and exclusively rely on this final version of `build_layers.txt` for layered building.

Use the **`ros-oe-eur-init`** skill to add the upgraded packages to the EUR project.
Then, use the **`ros-oe-eur-build`** skill to trigger the cloud builds using the `build_layers.txt`.
Wait for the builds to complete. If any build fails, use your agent capabilities to read the build logs, fix the compilation error locally, push the fix, and rebuild.

### Phase 5: Development Board Testing with EUR Repository
Use the **`ros-oe-board-test`** skill to validate the packages on the physical development board.
The skill provides a master orchestrator script. You must follow the skill's documentation to invoke the Master Orchestrator, which automatically handles L0 (Smoke & Custom tests) and L1 (On-board Incremental Build & Test) phases.
**Crucial**: If the orchestrator halts with a `[HALT: CODE]`, you MUST read the Agent Action Directive in the output, use bash/grep to diagnose the board's environment or source code, apply the fix, and rerun the orchestrator.

### Phase 6: Community PR Submission
Use the **`ros-oe-pr-submit`** skill to finalize the package upgrade. The skill will squash commits, sign them off, push to GitCode, and automatically open a Pull Request against the official `src-openeuler` repository with semantic Chinese descriptions.

### Phase 7: Official Release and Verification
This phase is used to seamlessly release the code packages that have been verified in the personal environment to the official EUR project.

**Execution Steps:**
1. **[Manual Intervention - Token Switch]**: As the first step of Phase 7, you MUST **pause the task** and prompt the user: "Preparing to enter the official EUR release phase. Please manually update the COPR authentication Token (if necessary). Reply to continue once updated."
2. **[Switch Configuration]**: After receiving user confirmation, modify the environment configuration file `openeuler_ros_upgrader_env.yaml`, updating `current_active_eur_project` to the value of `official_eur_project`.
3. **[EUR Initialization]**: Call the `ros-oe-eur-init` skill to batch associate the packages with the official EUR project based on the final package list (directly using the verified code source from the personal GitCode repository).
4. **[EUR Cloud Build]**: Call the `ros-oe-eur-build` skill to trigger and build layers **strictly following the updated `build_layers.txt` order**.
5. **[Official Source Board Smoke Test]**: Call the `ros-oe-board-test` skill (configured for L0 smoke testing mode) to let the dev board pull the newly built official source RPM packages for installation and basic validation, ensuring the released packages are usable on real devices.

**🛑 Phase 7 CRITICAL RULES (Absolute Taboos):**
- **NO Code Modifications**: It is strictly forbidden to modify any code on GitCode (including spec and patch files) during Phase 7. Directly reuse the branches that have been verified in the personal namespace.
- **NO pkg-update Execution**: Skip all dependency re-analysis and local code update processes (`ros-oe-pkg-update`).
- **Modification Confirmation Mechanism**: If a highly exceptional situation occurs requiring a Git push modification in this phase, you **MUST ask the user first** and obtain explicit authorization (in principle, all modifications should be closed before Phase 6).

## Dependency & Package Resolution Strategy (The Oracle Board)

**CRITICAL: NEVER USE THE LOCAL HOST FOR DEPENDENCY RESOLUTION.** 
The machine you are executing commands on is likely Ubuntu or a different environment. You MUST NOT run local commands (like `apt search`, `dpkg`, or local `find`) to guess if an openEuler package exists, what its name is, or where its `.so`/`.cmake` files are installed. You MUST NOT hallucinate package names based on CentOS/Fedora knowledge either.

Your **Single Source of Truth (The Oracle)** for the target openEuler environment is the physical development board configured in `openeuler_ros_upgrader_env.yaml`. The board has the exact `dnf` repositories configured for our target openEuler version.

**When you need to verify a dependency name (e.g., in Phase 3 while writing `BuildRequires`, or Phase 4/5 debugging errors), you MUST execute `dnf` queries directly on the board via SSH:**

1. **Retrieve Credentials**: First read `board_ip`, `board_username`, and `board_password` from `openeuler_ros_upgrader_env.yaml`.
2. **Execute Remote Queries**: Use `sshpass` to run commands on the board without interaction:
   - **Check if package exists/guess name**: `sshpass -p "$board_password" ssh -o StrictHostKeyChecking=no $board_username@$board_ip "dnf search <keyword>"`
   - **Check package info/version**: `sshpass -p "$board_password" ssh -o StrictHostKeyChecking=no $board_username@$board_ip "dnf repoquery --info <exact_package_name>"`
   - **Find which package provides a missing library or file**: `sshpass -p "$board_password" ssh -o StrictHostKeyChecking=no $board_username@$board_ip "dnf provides '*/libmissing.so.1'"`
   - **List files inside a package**: `sshpass -p "$board_password" ssh -o StrictHostKeyChecking=no $board_username@$board_ip "dnf repoquery -l <package_name>"`

**Rule of Thumb for Missing Packages**: If a package or file cannot be found via the board's `dnf` repositories, you MUST assume openEuler currently does NOT provide it. Do NOT keep guessing names from other distros. Instead, you must either:
- Package it from source yourself (e.g., generate a new spec for a missing 3rd-party library).
- Modify the `%cmake` configuration to disable the feature that requires this missing dependency.
- Ask the user for guidance if the missing dependency is critical and cannot be disabled.

### Code Quality Standards:

- **Zero Hardcoded Paths/Names/Versions in Specs (CRITICAL)**: openEuler ROS packages strictly define the base package name and version via macros at the very top of the file:
  ```spec
  %define RosPkgName      controller-interface
  Name:           ros-%{ros_distro}-%{RosPkgName}
  Version:        2.54.0
  ```
  Everywhere else in the spec (like `%prep`, `%autosetup`, `%build`, `%install`, and `%files`), you MUST NEVER hardcode the package name or version. You MUST strictly use macros like `%{RosPkgName}`, `%{name}`, and `%{version}`.
  - ❌ **Ugly/Bad**: `%autosetup -c -n controller-interface-2.54.0` or `cd fastcdr-1.0.24`
  - ✅ **Beautiful/Good**: `%autosetup -n %{RosPkgName}-%{version} -p1` or `cd %{RosPkgName}-%{version}`
  This ensures the spec file is future-proof and doesn't break on the next version bump.
- **Clean Patches**: Each patch should be minimal, focused, and apply cleanly
- **Git Commits**: All commits MUST be signed-off using the `-s` flag (`git commit -s -m "..."`) and written in English. Pull Request titles and descriptions MUST be in Simplified Chinese.
- **Clear Documentation**: Every change must be well-documented in spec files and patch descriptions
- **Upstream Alignment**: Prefer upstream solutions over local workarounds when possible
- **Reproducibility**: Ensure builds are reproducible across different environments
