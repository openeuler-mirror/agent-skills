# ROS Upgrade PR Submitter

This skill is designed to help users take a series of scattered commits located in their personal Fork repositories (e.g., within `src-openeuler-forked/`) that have been locally verified, reorganize them (Squash), intelligently summarize them into semantic descriptions, force push, and finally submit high-quality Pull Requests to the official `src-openeuler` repositories.

**New in this version**: It fully integrates robust GitCode V5 API logic to prevent 404 namespace errors, auto-updates existing PRs to prevent duplication, and enforces semantic, categorized Markdown PR descriptions generated by the AI agent.

## Prerequisites & Requirements
1. **Workspace Environment**: Ensure that an `openeuler_ros_upgrader_env.yaml` configuration file exists in the current workspace, containing the `ros_upstream_init_dir`, `current_active_eur_project`, and your GitCode account information.
2. **GitCode Credentials**: Ensure your GitCode Private Token is saved in `~/.config/gitcode`.
3. **Working Directory**: All modifications should be located within the `src-openeuler-forked/` directory.

## Workflow

When executing this skill, **strictly follow the six steps below** and do not skip any:

### 1. Backup First
**[Mandatory Requirement]** Before performing any destructive Git operations (like `git reset` or `git commit --amend`), you **MUST** perform a complete local backup of the `src-openeuler-forked` directory containing all your work.
```bash
BACKUP_DIR="src-openeuler-forked-backup-before-pr-$(date +%Y%m%d%H%M%S)"
cp -a src-openeuler-forked "$BACKUP_DIR"
echo "Full backup completed to: $BACKUP_DIR"
```

### 2. Filter Non-ROS Packages
For each repository where a PR is to be submitted, you must verify whether it is a genuine ROS package:
1. Read `ros_upstream_init_dir` from `openeuler_ros_upgrader_env.yaml`.
2. Check if the directory `ros-oe-upstream-init/output/repo/<repo_name>` exists.
3. **If it does not exist**: The repository is a non-ROS third-party library (like `nanoflann`, `gtsam`, `opencv`, etc.), **skip it directly**, and do not submit a PR for it within this skill.
4. **If it exists**: Continue processing. Note: If a repository contains multiple packages (like `navigation2`), only submit one PR containing all changes for the entire repository.

### 3. Fetch & Diff
Synchronize the state of the target repository and extract all modifications made during this period:
```bash
cd src-openeuler-forked/<repo_name>
git fetch upstream humble
# Get all new logs and detailed Diffs compared to the official baseline branch
git log upstream/humble..HEAD --oneline
git diff upstream/humble...HEAD
```
**[Memory Restoration]**: You MUST also read `reports/02_update_summary.md` (if it exists) to recall why certain patches were modified, deleted, or why specific compilation flags were added during the `ros-oe-pkg-update` phase.

### 4. Semantic AI Review & PR Description Generation
After extracting the Diff, Log, and reading the update summary, do not commit immediately. **You must act as the Agent to self-review these modifications and generate a Semantic PR Description.**

#### Guidelines for the PR Description (`pr_desc_zh.txt`):
1.  **Format**: MUST use structured Markdown.
2.  **Categorization**: Group features by file type or module (e.g., `Spec modifications`, `Patch updates`).
3.  **Semantic Tags**: Explicitly mark changes with `[新增] (Added)`, `[修改] (Modified)`, or `[删除] (Deleted)`.
4.  **Real Modifications**: Do not guess or invent features. Explain *why* changes were made based on the actual Git Diff (e.g., "Updated macro `%global ros_version` to align with upstream").
5.  **EUR Build Link**: Extract the `current_active_eur_project` from `openeuler_ros_upgrader_env.yaml`. Generate the EUR package build URL and include it at the bottom of the PR description to provide reviewers with build verification.
    *   URL Format: `https://eur.openeuler.openatom.cn/coprs/{current_active_eur_project}/package/{package_name}/`
    *   Example: `[EUR 构建记录](https://eur.openeuler.openatom.cn/coprs/your-gitcode-username/your-eur-project/package/rclcpp/)`
6.  **No Testing Mentions**: DO NOT mention the dev board test environment, IPs, or local test scripts, as these are personal dev environments.

*If anomalies (like massive accidental deletions) are found during the diff review, stop immediately and report to the user.*

### 5. Squash & Sign-off
**[Configuration Repair Protection]** Check and clear any potentially broken local Git account configurations before committing:
```bash
git config --local --unset user.name || true
git config --local --unset user.email || true
```

Compress all scattered commits into a single commit and generate a highly detailed Commit Message in pure English.
- **Commit Message Standard (Pure English)**: Explain the context clearly (why a spec macro was modified, why a patch was added).
- **Execute Squash and Sign-off**:
```bash
# Undo all previous independent commits and put all modifications back into the staging area
git reset --soft upstream/humble
# Execute the commit with the signed-off-by signature using the generated message
git commit -s -F commit_message.txt
```

### 6. Push & Create GitCode PR
1. **Force Push Code**: `git push --force origin humble` (Force push to the personal Fork repository).
2. **PR Mode Judgment & Title Standard**:
   - **[Mandatory Requirement] The PR title MUST be entirely in Chinese** (for manual review by the Maintainer).
   - **Draft Mode (Default)**: Add the prefix `[WIP] ` to the title, e.g., `[WIP] 将 message_filters 升级至 4.3.14 版本`. This indicates that a manual secondary review is needed on the GitCode page later.
   - **No-Review Mode** (If the user explicitly declares it): Do not add `[WIP]`.
3. **Invoke Robust Python PR Manager**:
Use the `submit_pull_request.py` script provided with this skill. This script uses GitCode API V5 to reliably resolve repos and prevent errors. **If a PR already exists, it will automatically update it.**

```bash
python3 ~/.claude/skills/ros-oe-pr-submit/scripts/submit_pull_request.py create \
    --pkg "<repo_name>" \
    --author "<your_username>" \
    --title "[WIP] 升级 xxx 到 xxx 版本" \
    --desc "$(cat pr_desc_zh.txt)" \
    --branch "humble"
```

After execution is complete, please output the successful PR link (or the updated PR link) to the user. Loop through steps 2 to 6 for multiple repositories.

## Output Language Rules

1.  **INTERNAL REASONING & TOOL USAGE**: All internal thinking, reasoning, and tool calls (like reading files, searching, executing bash commands, reading logs) MUST be conducted exclusively in **English**.
2.  **GIT COMMIT MESSAGES**: All git commit messages must be in **English**, clear, descriptive, and accurately reflect the changes. You MUST include the `-s` flag in your git commits to add the `Signed-off-by` line required by openEuler DCO.
3.  **USER-FACING OUTPUT (FINAL DELIVERABLES)**: Only the final, user-facing output MUST be entirely in **Simplified Chinese (简体中文)**. This includes:
    *   Summaries or reports provided to the user in the chat interface.
    *   Markdown log files.
    *   Pull Request titles and descriptions.

When reviewing code diffs, checking API responses, and squashing commits, conduct all your system interaction and internal thought processes in English, but deliver the final structured PR description and chat response to the user in Chinese.
