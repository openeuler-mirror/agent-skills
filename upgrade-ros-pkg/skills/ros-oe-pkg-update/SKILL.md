# ros-oe-pkg-update

Used to locally update upstream ROS package spec files, patches, and tarballs into the openEuler repository.

## Skill Directory Structure

```text
<skill_dir>/ros-oe-pkg-update/
├── SKILL.md              # Skill documentation (this file)
├── README.md             # Quick start guide
├── scripts/
│   ├── update_local_packages.py  # Main script
│   ├── check_workspace_status.sh  # Script to check repository status
│   └── push_package_updates.sh  # Batch commit and push script
└── references/
    ├── git-push-best-practices.md  # Git push best practices (LFS, force push, etc.)

```

## Script Location

Main script path: `<skill_dir>/ros-oe-pkg-update/scripts/update_local_packages.py`

## Output File Location

All output files are generated in the directory specified by `--openeuler-dir`.

## Features

1. **Smart Spec Update**: Updates openEuler spec files based on upstream specs.
2. **Patch Preservation**: Automatically restores openEuler-specific patch instructions.
3. **Tarball Management**: Automatically deletes old tarballs and copies new ones.
4. **Diff Recording**: Records spec upgrade differences for git commits.
5. **Code Agent Integration**: Automatically invokes the agent for deep analysis upon encountering unknown differences.
6. **Automated Processing**: Supports batch processing of multiple packages from a dependency list file.

## Workflow

### Pre-update Verification (CRITICAL)
Before updating any package, you MUST verify if it has upstream tracking issues. Check the log files generated by `ros-oe-upstream-init`:
1. Check `<upstream_cache_dir>/output/version_mismatch.log` for branch mismatch issues.
2. Check `<upstream_cache_dir>/output/bloom_release_repos.log` for repository URL issues (-release repos).

If the package exists in EITHER log:
- For mismatches: append the correct branch to `<upstream_cache_dir>/scripts/ros/<ros_distro>/ros-version-fix`
- For bloom repos: append the correct upstream URL to `<upstream_cache_dir>/scripts/ros/<ros_distro>/ros-url-fix`
- Delete its old source directory: `rm -rf <upstream_cache_dir>/output/src/<repo_name>*`
- Regenerate upstream data: `bash <upstream_cache_dir>/scripts/ros-upstream-setup.sh`

### Executing the Update

Executes the following steps for each package:

1. **Create backup file**: Always create `<spec>.backup` regardless of whether modifications are needed.
2. **Delete old tarball**: Delete the tarball referenced in the old spec from the openEuler repo.
3. **Overwrite spec file**: Overwrite the openEuler spec with the upstream spec.
4. **Analyze differences using git diff**: Identify modification points and types.
5. **Determine action based on difference type**:
   - Expected differences (version, Source, prep, etc.): continue processing.
   - Patch differences: handle according to four scenarios or invoke agent analysis.
   - Other unknown differences: invoke code agent for deep analysis.
6. **Copy new tarball**: Copy the tarball used in the new spec from the upstream repo to the openEuler repo.
7. **Record differences**: Record upgrade differences and reasons to the workspace file.
8. **Delete backup file**: Delete `<spec>.backup` immediately after completing the package upgrade.

## Usage

```bash
skill: "ros-oe-pkg-update", args: "--openeuler-dir /path/to/src-openeuler --upstream-dir /path/to/ros-oe-upstream-init/output/repo --package-list-file dependency_order.txt"
```

- `--upstream-dir <path>`: upstream tarball directory (Required)

  - Format: One package name per line.
  - Supports `#` prefixed comment lines (automatically ignored).
  - Example:


## Processing Logic Details

### Agent Fallback Mechanism for Non-ROS System Dependencies (non_ros_manual_update)

Since `ros-oe-upstream-init` mainly resolves dependencies based on ROS `package.xml`, the tool usually cannot automatically generate upstream specs and tarballs for underlying pure C/C++ or Python non-ROS libraries (e.g., `xtl`, `xtensor`, etc.).

To ensure the ROS upgrade chain remains unbroken, this skill triggers a special `non_ros_manual_update` request to the `openeuler-ros-upgrader` Agent when it detects that the `upstream_dir` is missing the corresponding package.

**Standard Agent Handover Workflow (Experience Summary)**:

1. **Source Acquisition**: Locate the required version via GitHub Release/Tags API, and use `curl` / `wget` to download the source `.tar.gz` to the local workspace.
2. **Write or Update `.spec` file**:
   - **Architecture Declaration**: If it is a Header-only library, you **must** declare `BuildArch: noarch` inside `%package devel` (or globally).
   - **Debug Package Suppression**: For Header-only libraries, it is **strongly recommended** to explicitly add `%global debug_package %{nil}`. If not suppressed, the openEuler RPM build environment will throw an error and abort the entire build when looking for ELF files to extract debug symbols.
   - **Dependency Constraints**: Accurately declare `BuildRequires` and `Requires` with specific version constraints (e.g., `>= 0.7.0`) to avoid ecological conflicts caused by blindly using the latest version.
3. **Deep Control of CMake Build Options**:
   - Do not just write a single `%cmake_build`.
   - You must probe available macros via `cmake .. -L`. Unnecessary strong dependency backends (like SIMD, TBB, OpenMP, etc.) or test modules (`-DBUILD_TESTS=OFF`) should be explicitly disabled in the `%cmake` stage to ensure a high compilation success rate in minimalist environments.
4. **Deprecate `%cmake_build` macro**:
   - In the openEuler environment, the `%cmake_build` and `%cmake_install` macros often cause `command not found` or missing `CMakeCache` errors due to historical baggage, Ninja generator conflicts, or disconnected external build paths.
   - **Defensive Rule**: Uniformly use the most basic `%make_build` and `%make_install` macros instead.
   ```rpm
   %build
   %cmake -DBUILD_TESTS=OFF
   %make_build

   %install
   %make_install
   ```
5. **Accurately Locate `%files` Paths**:
   - For CMake-generated libraries (especially Header-only), `.cmake` config files and `.pc` files are often placed in `%{_libdir}` instead of the expected `%{_datadir}` by `GNUInstallDirs`.
   - It is recommended to perform a local trial run with `rpmbuild` up to the `%install` stage to verify the final generated file tree. Use this to absolutely calibrate the paths in `%files`, avoiding critical RPM errors like "installed (but unpackaged) file(s) found".

### Intelligent Knowledge Accumulation (package_fix)

When analyzing differences between the old openEuler spec and the new upstream spec, the Agent MUST NOT blindly inherit old patches. Instead, it must intelligently extract and transform historical adaptations into robust rules stored in `~/.claude/skills/ros-oe-upstream-init/scripts/package_fix/<package_name>/`:

1. **Statically Analyze Old Bug Fix Patches**: If an old patch fixes an upstream bug (e.g., missing `#include <map>`), check the new upstream source code. If upstream has merged the fix, **discard the patch**. Do NOT port it.
2. **Transform Test Disabling Patches**: If an old patch simply comments out `add_subdirectory(test)` or demo folders, **DO NOT port the patch**. Instead, write `-DBUILD_TESTING=OFF \` (or similar CMake flags) into the `cmake_args.fix` file for that package.
3. **Preserve Custom Compiler Flags**: If the old spec has openEuler-specific security flags or path hardcodings (like `/usr/lib64`), abstract them into standard CMake parameters and store them in `cmake_args.fix`. Note: the contents in `cmake_args.fix` can be separated by spaces or newlines, but if you break lines, you must add a trailing backslash `\` EXCEPT for the very last line.
4. **Vendor Tarballs Dynamic Update**: If a vendor package relies on offline tarballs (e.g., `ignition-math6-vendor`) due to OBS network isolation:
   - Parse the new upstream `CMakeLists.txt` for the new `URL` or `GIT_TAG`.
   - **Download the new tarball** to the `package_fix/<pkg>` directory.
   - Update `source.fix`, `prep.fix`, and the CMake replacement Patch with the new version.
   - **Never blindly reuse the old tarball**.
   - For Rust/Cargo packages (like `zenoh`), you must run `cargo vendor` in an online environment to generate a new offline dependencies tarball.
5. **Strict No-Hardcoding Rule**: Ensure all `prep.fix` contents and patches use dynamic macros like `%{version}` and `%{RosPkgName}`. Never hardcode absolute version strings (e.g., `cd package-1.2.3`).

### Spec File Update Strategy

**Always backup first, then analyze differences with git diff after overwriting**:

1. **Create backup file**: Regardless of whether a single line needs modification, create `<spec>.backup` first.
   ```bash
   cp <old_spec> <old_spec>.backup
   ```
2. **Overwrite spec file**: Overwrite `old_spec` with the `upstream_spec`.
   ```bash
   cp <upstream_spec> <old_spec>
   ```
3. **Analyze differences with git diff**:
   ```bash
   cd <openeuler_dir>/<package_name>
   git diff <package_name>.spec > /tmp/<package_name>_spec_diff.txt
   ```
4. **Determine action based on difference type**:
   - **Version, Source, prep, build, etc.**: Expected differences, continue processing.
   - **Patch instruction differences**: Handle according to the four scenarios (see below).
   - **Other unknown differences**: **Invoke code agent for deep analysis**.
     - Use git diff output, combined with upstream/downstream git logs.
     - Analyze difference possibilities and impacts.
     - Provide specific recommendations and processing solutions.
5. **Delete backup file**: Delete `<spec>.backup` immediately after package upgrade completion.
6. **Avoid redundant git status**: Ensure no temporary files are left in the working directory.

### Tarball Processing

**Avoid using special name matching like `.orig.tar.gz`**, ensuring the skill can be reused in every upgrade:

- ✅ **Correct Approach**: Get the tarball name by parsing the spec file.
  ```bash
  # Extract Source0 field from spec file
  tar_name=$(grep "^Source0:" <spec_file> | awk '{print $2}')
  ```
- ❌ **Incorrect Approach**: Use glob pattern matching `*.orig.tar.gz`.

### Detailed Patch Handling Logic

**Four Scenarios of Patch Differences**:

**Scenario A: Old has patch, New has no patch**
- Action: Restore patch to new spec.
- Command:
  ```bash
  grep "^Patch[0-9]:" <old_spec.backup> >> <new_spec>
  ```
- Reason: openEuler customized patches need to be preserved.

**Scenario B: Old has Patch A, New has Patch A**
- Action: No modification needed, continue processing.
- Reason: Patch unchanged, normal upgrade.

**Scenario C: Old has Patch A, New has Patch B (Patches differ)**
- Action: **Invoke code agent for deep analysis**.
- Analysis Content:
  1. Read git diff output.
  2. View upstream/downstream git log:
     ```bash
     cd <upstream_repo_dir>
     git log --oneline -20 <patch_file>
     ```
  3. Compare patch file contents:
     ```bash
     diff <old_patch> <new_patch>
     ```
  4. Provide analysis conclusion:
     - Might be a patch content update.
     - Might be a patch name change.
     - Upstream might have merged the fix.
     - Patch dependencies might have changed.
- Recommendation Options:
  - Merge the contents of both patches.
  - Delete old patch, keep new patch.
  - Keep old patch, delete new patch.
  - Re-review the necessity of the patch.

**Scenario D: Old has no patch, New has patch**
- Action: Record differences, copy new patch to openEuler repo, continue processing.
- Copy new patch:
  ```bash
  # Find patch file from upstream directory
  new_patches=$(grep "^Patch[0-9]:" <new_spec> | awk '{print $2}')
  for patch in $new_patches; do
      upstream_patch=$(find <upstream_dir> -name "$patch" | head -1)
      if [ -n "$upstream_patch" ]; then
          cp "$upstream_patch" <openeuler_dir>/<package_name>/
      fi
  done
  ```
- Reason: New upstream patches need to be synced to the openEuler repository.

**Patch files themselves**: The patch files themselves will not be deleted; only the instructions in the spec are processed.

### Code Agent Invocation Mechanism

**When encountering an unexpected difference type**:

1. **Pause processing for the current package**.
2. **Invoke code agent for deep analysis**:
   - Read git diff output.
   - View git history:
     ```bash
     cd <upstream_repo>
     git log --oneline -20
     cd <openeuler_repo>
     git log --oneline -20
     ```
   - Analyze possibilities and impacts.
   - Provide specific recommendations.
3. **Wait for user confirmation**: Pause and inform the user of the agent's analysis.
4. **Continue based on user choice**:
   - Adopt agent recommendation: Continue applying changes.
   - Skip current package: Mark as failed, continue to the next.
   - Provide alternative: Let user specify handling method.

## Error Handling

### Common Errors and Solutions

1. **Cannot find openEuler spec**
   - Check if openEuler directory path is correct.
   - Verify package name spelling (underscore vs hyphen).
2. **Cannot find upstream spec**
   - Check upstream directory path.
   - Verify upstream package is downloaded.
3. **Cannot find tarball**
   - Check if upstream tarball exists.
   - Verify tarball name matches Source field in spec.
4. **Patch restoration failed**
   - Check if patch file exists.
   - Verify patch naming format (Patch0, Patch1, etc.).
5. **Git repository issues**
   - Confirm openEuler directory is a git repository.
6. **Agent analysis timeout**
   - Log timeout error.
   - Provide git diff for manual review.

## Push to GitCode

### Large Tarball Handling (> 10MB)

**⚠️ IMPORTANT**: For large tarballs (> 10MB), **they MUST be split using `split` in this phase**, instead of using Git LFS.

#### Why not use Git LFS?
EUR build environment **does not support git lfs**:
- EUR's rpkg tool does not execute `git lfs pull`.
- It reads the LFS pointer file instead of the real tarball.
- Causes build failure: `tar: This does not look like a tar archive`.

#### Standard Processing Workflow

**Step 1: Detect tarball size**
```bash
tar_size=$(stat -c%s "${upstream_tar}")
tar_size_mb=$((tar_size / 1024 / 1024))
if [ $tar_size_mb -gt 10 ]; then
    echo "⚠️ Large tarball detected (${tar_size_mb}MB), splitting required"
fi
```

**Step 2: Split the large tarball**
```bash
rm -f <package>-<version>.tar.gz
split -b 8M <upstream_tar> <package>-<version>.tar.gz.
```

**Step 3: Modify spec file**
```spec
Source0:        %{RosPkgName}-%{version}.tar.gz.aa
Source1:        %{RosPkgName}-%{version}.tar.gz.ab

%prep
cat %{SOURCE0} %{SOURCE1} > %{RosPkgName}-%{version}.tar.gz
tar -xzf %{RosPkgName}-%{version}.tar.gz
%autosetup -T -D -p1 -n %{RosPkgName}-%{version}
```
**%autosetup parameter notes**:
- `-T`: **T**arball processing - Do not unpack again.
- `-D`: **D**irectory preservation - Do not delete unpacked directory.
- `-p1`: Patch prefix - Use -p1 when applying patches.
- `-n <name>`: **n**ame - Specify unpacked directory name.

**Step 4: Commit to Git repository**
```bash
git add <package>-<version>.tar.gz.*
git add <package>.spec
git commit -s -m "Upgrade <package> to <version> with split tarball"
git push origin <branch>
```

## EUR Build Notes

### Patch Generation Specification

EUR uses `patch -p1 --fuzz=0` to apply patches.
**Must generate patches using Git**:
```bash
tar -xzf package-version.tar.gz
cd package-version
git init && git add . && git commit -s -m "original"
vim src/file.cpp
git diff > ../package-fix.patch
```

### Spec File %autosetup Configuration

**Incorrect**: `%autosetup -c -n %{name}-%{version} -p1`
**Correct**: `%autosetup -n %{RosPkgName}-%{version} -p1`

**Key points**:
- Remove `-c` parameter (do not create extra directory).
- Use `%{RosPkgName}` instead of `%{name}`.

### CMake Source Directory Path
After modifying `%autosetup`, the cmake source directory needs adjustment:
**Incorrect**: `../%{RosPkgName}-%{version}`
**Correct**: `..`

### Script Execution Logic

1. **Script processes automatically**: Expected differences, Patch Case A, B, D.
2. **Script records but skips**: Patch Case C, Unknown differences (saves to `agent_analysis_request.json`).
3. **Agent Post-Processing**:
   - Reads `agent_analysis_request.json`.
   - Calls Code Agent for each package.
   - Waits for user decision.
   - **Applies decisions directly without re-running the script**.

### Why not re-run the script?
- Prevents redundant processing of already completed packages.
- Saves time.
- Uses preserved backup files directly.
