# ros-oe-eur-build

Used to batch trigger cloud-side builds of ROS packages in an openEuler EUR (COPR) project.

## Use Cases

- Batch build ROS packages on the openEuler EUR (COPR) platform.
- Trigger SCM builds from Git repositories (src-openeuler or personal forks).
- Poll build status and collect results.
- Analyze reasons for build failures and provide fix recommendations.
- Complete the build workflow after spec merging and EUR repository initialization.

## Usage

```bash
skill: "ros-oe-eur-build", args: "--workspace-dir <path> --package-list-file <file> [--copr-project <project>] [--branch <branch>] [--force]"
```

### Parameters

- `--workspace-dir`: Workspace directory path (containing src-openeuler or package directories).
- `--package-list-file`: Package list filename (relative to workspace-dir). It is HIGHLY recommended to use `build_layers.txt` generated by `ros-oe-pkg-prep` for parallel layer-by-layer building.
- `--copr-project`: COPR project name (Default: `your-gitcode-username/your-eur-project`).
- `--mode`: Repository mode - `personal` (for personal repo validation) or `official` (for official repo builds, default).
- `--username`: Personal repository username (Default: `your-gitcode-username`, used only in personal mode).
- `--branch`: Git branch (Default: `humble`).
- `--poll-interval`: Status polling interval in seconds (Default: 60).
- `--max-wait`: Maximum wait time in minutes **per package** (Default: 240, i.e., 4 hours).
- `--force`: (Optional) Ignore the local success cache (`eur_build_success.list`) and force a complete rebuild of all packages in the list.

**IMPORTANT**: `--max-wait` is an independent timeout for *each* package, not the total timeout. For 10 packages, the theoretical maximum wait time is 10 × 4 hours = 40 hours. Adjust this parameter based on the number and complexity of packages:
- **Few simple packages** (1-5): 120-180 minutes.
- **Medium scale** (5-20): 240 minutes (Default).
- **Large scale builds** (20+): 360 minutes or longer.

### Examples

```bash
# Personal repo mode (iterative validation)
skill: "ros-oe-eur-build", args: "--workspace-dir ~/Desktop/test/ros2cli_test --package-list-file test_build_order.txt --mode personal"

# Official repo mode (formal build, default)
skill: "ros-oe-eur-build", args: "--workspace-dir ~/Desktop/test/ros2cli_test --package-list-file test_build_order.txt --mode official"

# Specify COPR project and personal username
skill: "ros-oe-eur-build", args: "--workspace-dir ~/Desktop/test --package-list-file packages.txt --copr-project myuser/my-ros-project --mode personal --username myuser"

# Complete workflow (spec merge → EUR init → build)
# 1. Run ros-oe-pkg-update first to complete spec merging.
# 2. Run ros-oe-eur-init to initialize the EUR repository (supports personal/official modes).
# 3. Finally, run this skill to trigger the build (using the same mode and username).
```

## Prerequisites

1. **copr-cli is configured**:
   ```bash
   # Verify configuration
   copr-cli whoami
   ```
   If it fails, configure the EUR API token in `~/.config/copr`:
   ```bash
   # Get token from https://eur.openeuler.openatom.cn/coprs/<user>/api/
   mkdir -p ~/.config
   cat > ~/.config/copr << EOF
   [copr-cli]
   login = <your_login>
   token = <your_token>
   copr_url = https://eur.openeuler.openatom.cn
   EOF
   chmod 600 ~/.config/copr
   ```

2. **Package list is ordered by dependencies**: The skill will build sequentially or layer-by-layer based on the list, ensuring dependencies are built before dependents.

3. **EUR repository is initialized**: It is recommended to run `ros-oe-eur-init` first to ensure packages are added to the EUR project.

## Workflow

### Mode Specifications

Supports two build modes, which should match the mode used in `ros-oe-eur-init`:

1. **personal mode (Personal repo iterative validation)**
   - Git repository: `https://gitcode.com/{username}/{package-name}.git`
   - Use case: Iterative development and validation on a personal forked repository.
   - Default username: `your-gitcode-username`.
   - It is recommended to validate in this mode first before switching to official mode.

2. **official mode (Official repo formal build)**
   - Git repository: `https://gitcode.com/src-openeuler/{package-name}.git`
   - Use case: Formal builds from the openEuler official repository.
   - This is the **default mode**.

### Package Name, Repository Name, and Spec File Naming Conventions

**IMPORTANT**: ROS 2 RPM packages have three levels of naming. You must understand the conversion relationships between them:

1. **Package Name**
   - Uses underscores as separators.
   - Examples: `iceoryx_hoofs`, `rosidl_cli`, `foonathan_memory_vendor`.

2. **Repository Name**
   - Might differ from the package name, mapping via `ros-projects.list`.
   - Example: `iceoryx_hoofs` package → `iceoryx` repository.
   - Example: `rosidl_cli` package → `rosidl` repository.

3. **Spec File Name**
   - **Must use hyphens**, even if the package name uses underscores.
   - Example: `iceoryx_hoofs` package → `iceoryx-hoofs.spec`.
   - Example: `rosidl_cli` package → `rosidl-cli.spec`.
   - This is a strict ROS 2 convention; spec filenames uniformly use hyphens.

**Automatic Conversion Rules**:
- The skill automatically converts between underscore and hyphen versions of the package name to find mappings in `ros-projects.list`.
- The spec filename is automatically converted from the package name (underscore → hyphen).

### 3. Read Package List and Map Repository Names
Reads packages from the list and uses the `ros-projects.list` file to find actual repository names:
```text

```

**Location of ros-projects.list**:
```text
<ros_upstream_workspace>/output/ros-projects.list
```

### 4. Trigger Build

**IMPORTANT: How to correctly invoke EUR build commands**

In the EUR (COPR) environment, `copr-cli` provides different commands for building and registering. **Do NOT confuse their parameters**:

1. **`copr-cli add-package-scm`**: Used to **register/add** a package to the project, requiring `--name`, `--clone-url`, `--commit`, etc. This step has already been completed in the `ros-oe-eur-init` skill.
2. **`copr-cli build-package`**: Used to trigger a build for an **already registered** package. It **cannot** and does not need to receive SCM parameters like `--clone-url` or `--commit`. Its inputs are extremely simple.

When executing a build for each package, directly use the following command:

```bash
copr-cli build-package   --name <package-name>   --nowait   <copr-project>
```

**Incorrect Approach** (Will cause build failure or unrecognised parameter errors):
❌ `copr-cli build-package --name <pkg> --clone-url <url> <project>` (Confuses build-package with add-package-scm)
❌ `copr-cli buildscm --name <pkg> ...` (buildscm does not accept --name parameter)

**Correct Approach**: Since `ros-oe-eur-init` has already saved configurations like `clone-url` and `commit` in the EUR project, we only need to use `build-package` to wake it up.

### 5. Status Polling
For each triggered package, periodically poll the build status:
```bash
copr-cli get-package-status <copr-project> <package-name>
```

Status types:
- `pending`: Waiting in queue
- `running`: Currently building
- `succeeded`: Build successful
- `failed`: Build failed
- `canceled`: Canceled
- `skipped`: Skipped

### 6. Results Collection
Collect upon build completion:
- Build status (succeeded/failed)
- Build duration
- Build log URL
- Failure reason (if failed)

### 7. Failure Analysis
For failed builds:
1. Download build logs.
2. Analyze error causes (compilation errors, missing dependencies, spec issues, etc.).
3. Provide:
   - Failure summary.
   - Key error messages.
   - Potential fix recommendations.
   - Invoke the Claude Code agent for deep analysis if necessary.

### 8. Fixing and Resuming (Smart Retry & Force Rebuild)
If a layer fails due to one or more packages:
- **Fix it locally**: Read the log, fix the code/spec, and push your changes to GitCode.
- **Resume the build**: Just run the exact same `ros-oe-eur-build` command again!
- **Smart Skip**: The script tracks successfully built packages in `<workspace-dir>/eur_build_success.list`. When you rerun the batch, it will automatically `[SKIP]` any packages in that layer (and previous layers) that have already succeeded, and **only** trigger builds for the failed ones. This perfectly prevents wasting cloud build resources.

**What if I NEED to rebuild a successful package?**
If an underlying dependency changed and you must force an upper-layer package to rebuild even if it previously succeeded, you have two options:
1. **Targeted Rebuild**: Simply open `<workspace-dir>/eur_build_success.list` and delete the line containing that package name. The script will trigger it again on the next run.
2. **Full Force Rebuild**: Add the `--force` flag to your `ros-oe-eur-build` command to completely ignore the success cache for this run.

### Important Warning: Package Renaming by EUR (ros-humble- prefix)

**EXTREMELY IMPORTANT: EUR automatically renames packages!**

When we create a package in the EUR project via `add-package-scm` (or the `ros-oe-eur-init` skill), we use its **short name** (e.g., `rclcpp`).
HOWEVER! When this package **successfully completes its SRPM build for the first time** on the EUR side, EUR reads its `.spec` file. Since the ROS package spec explicitly states `Name: ros-humble-rclcpp`, **EUR immediately renames the package in the project to `ros-humble-rclcpp`**!

What is the impact of this?
If the package has been renamed, and you try to execute `copr-cli build-package --name rclcpp ...` again or query `rclcpp` on the web page, EUR will report **`Error: No package with name rclcpp`**.

**Solutions and Operational Rules**:
1. The `trigger_eur_builds.sh` script has built-in compatibility (when it finds that `rclcpp` reports not found, it automatically retries with the `ros-humble-` prefix).
2. **For you as an Agent**: If you encounter a `No package with name xxx` error during any manual queries (like `copr-cli get-package`, checking status, etc.), **you MUST immediately realize it might have been renamed by EUR**. Please proactively add the `ros-humble-xxx` prefix and retry. Do not assume the package doesn't exist and fall into a loop.

## Common Issues

### 1. copr-cli Authentication Failed
**Error**: `Error: You have to provide API key`
**Fix**: Configure API token in `~/.config/copr` as described in prerequisites.

### 2. Package Not Added to EUR Project
**Error**: `Package '<name>' not found in project`
**Fix**: Run `ros-oe-eur-init` first to add packages to the project.

### 3. SCM Clone Failed
**Error**: `Failed to clone repository`
**Fix**:
- Check if GitCode repository exists.
- Verify repository name is correct.
- Confirm branch name (might be `main` instead of `master`).

### 4. Build Dependency Missing
**Error**: `Package dependency not found`
**Fix**:
- Ensure building in dependency order (layer-by-layer).
- Check if dependency packages built successfully.

### 5. Build Timeout
**Error**: `Build timeout`
**Fix**:
- Increase `--max-wait` parameter.
- Check COPR build queue congestion.
- View COPR Web UI for build progress.

### 6. Patch Application Failed - "No file to patch"
**Error**: `No file to patch. Skipping patch. 1 out of 1 hunk ignored`
**Cause**: EUR uses `patch -p1 --fuzz=0`, patches must use `a/` and `b/` prefixes.
**Fix**: Generate patches using git:
```bash
git init && git add . && git commit -m "original"
# Edit files
git diff > ../package-fix.patch
```

### 7. %autosetup Directory Structure Issue
**Error**: Patch format correct but still cannot find files.
**Cause**: `%autosetup -c -n %{name}-%{version}` creates an incorrect double-layer directory.
**Fix**: Modify spec file:
```spec
# Correct
%autosetup -n %{RosPkgName}-%{version} -p1
```

### 8. CMake Source Directory Path Error
**Error**: `CMake Error: The source directory "/builddir/build/BUILD/pkg-version/pkg-version" does not exist.`
**Cause**: Directory structure changed after modifying `%autosetup`.
**Fix**: Modify cmake source directory:
```spec
# Correct
%cmake3 ... ..
```

## Log Download Addressing Rules (Agent Knowledge Base)

During EUR builds, build logs are stored in different paths depending on the build stage and status. The `trigger_eur_builds.sh` script internally implements intelligent fallback polling downloads. But if the Agent needs to locate logs manually, follow these rules:

Assuming Build ID = `110966`, padded to 8 digits in the URL it becomes `00110966`.
Project path = `username/projectname` (e.g., `your-gitcode-username/your-eur-project`)

1. **SRPM Stage Logs (First stage executed)**
   - Path: `https://eur.openeuler.openatom.cn/results/<project>/srpm-builds/<build_id>/builder-live.log`
   - *(If the build completes and archives, it automatically gets a `.gz` suffix)*

2. **RPM Compilation and Installation Stage Logs**
   - At this point, it runs in a specific build environment (Chroot).
   - Default EUR chroot is generally: `openeuler-24.03_LTS-aarch64` or `openEuler-24.03-LTS-aarch64`.
   - Target folder: `<build_id>-<pkg_name>` (Note: If the package name was forcefully prefixed with `ros-humble-` by EUR, the `<pkg_name>` here is the prefixed format).
   - Path: `https://eur.openeuler.openatom.cn/results/<project>/<chroot>/<build_id>-<pkg_name>/builder-live.log`
   - *(Similarly, `.gz` after archiving)*
